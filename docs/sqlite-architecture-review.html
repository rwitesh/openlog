A calm, capable SQLite core—with a few sharp edges around recovery.

This is a review of the current local database and the persistence paths that make its promises real. It asks whether the design is appropriate for OpenLog today, not whether it is maximally normalized or enterprise-shaped.

7.5out of 10 today

Verdict: a good v1 for a single-person, local-first timeline. The relational center is clean and the backup validation is thoughtful. The priority is to close two recovery holes, not to replace the schema with a larger one.

The model

Small on purpose

The core is a sensible fit for OpenLog’s current retrieval lenses. Media lives in ordered JSON lists on an entry, while tags—where uniqueness, reuse, and relationship queries matter—are normalized.

entries← 1 : many →entry_tags← many : 1 →tags   +   settings

Why the JSON media columns are reasonable

They preserve display order, make the common “load an entry” path one row read, and avoid a join-heavy media model before OpenLog needs media-specific filtering or sharing. This is an intentional simplification, not a schema flaw.

What that choice gives up

SQLite cannot enforce each media item’s shape or answer “who else references this file?” efficiently. That matters for cleanup and imported-data validation; it does not yet require a wholesale media-table rewrite.

Protection layers

The good failure story

Atomic database writes

Create/update replaces an entry’s tag links in one SQLite transaction. A process-local FIFO lock serializes normal database operations, avoiding startup and write interleaving.

Relational guarantees

entry_tags rejects duplicate pairs and points only to existing entries and tags. Deleting an entry removes its links but leaves reusable tags intact.

Recovery-minded backup

WAL, snapshotting on the active connection, a media-deletion gate, staging, a durable restore journal, and rollback copies are all strong local-first choices.

The design gets the most important idea right: the timeline database is the source of truth; search and views are derived from it.

Not urgent

Useful polish, later

Reduce FTS churn

The update trigger runs after every entry update, even timestamp/media-only edits. Scope it to UPDATE OF text, location.

Keep the lock hard to bypass

getDatabase() exposes the raw handle. Current callers are disciplined; keeping it internal would preserve the serialization rule mechanically.

Scale tags only when needed

Prefix tag search uses instr(), which normally cannot use the unique key index. Tags are small; revisit only if profiling says it matters.

Suggested sequence

Improve resilience without redesigning the model

1 · Protect restore first

  • Journal before each irreversible move.
  • Make replay state-aware and idempotent.
  • Exercise every crash boundary in tests.

2 · Harden import truthfulness

  • Verify actual schema semantics.
  • Rebuild FTS during restore.
  • Reject invalid JSON/media references explicitly.

3 · Tidy file lifecycle

  • Reconcile orphans deterministically.
  • Check references before deleting media.
  • Decide and document the WAL durability level.
