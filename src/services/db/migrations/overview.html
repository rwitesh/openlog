OpenLog · database migration map

One small step forward at a time.

Today’s complete database is v1. When its stored shape changes, add exactly one new migration file. The app does the rest in order.

The version train
V1 · todayFresh baseline

v1.ts creates the complete current schema. Do not change it after release.

V2 · next changeOne forward move

Create v2.ts only for the database change from v1 to v2.

V3 · laterKeep moving forward

Register each new file once. The current version is derived automatically.

What happens on app start or restore
01 · READOpenLog reads SQLite’s user_version.
02 · APPLYIt runs only the missing migration files, in order.
03 · COMMITThe new version is written only if that step succeeds.
04 · PROTECTBackup restores migrate in staging before the safe swap.

Safe by design: a failed migration leaves the live timeline alone. A backup from a newer schema is rejected; it is never downgraded or guessed at.

When you next change stored data

Your four-point checklist

1. ADD

Create v2.ts with only the SQL/data conversion needed for v1 → v2.

2. REGISTER

Add { version: 2, up: migrateToV2 } after v1 in schema.ts.

3. ALIGN

Update types, reads, writes, and final-schema validation for the new shape.

4. PROVE

Test a fresh database, v1 → v2, and a restored backup → v2.
